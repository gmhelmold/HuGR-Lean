# HuGR-Lean Protocol V1 Wire Contract

**Implements:** WP1.1 / issue #21  
**Normative parent:** `docs/TECHNICAL_SPEC.md` §6  
**Status:** concrete wire refinement

This document records the executable JSON representation chosen for Protocol V1. It does not add semantic capabilities beyond HL-SPEC-001.

## Invocation

~~~text
hugr-lean filter --protocol 1
~~~

One process handles exactly one request.

~~~text
stdin   one JSON ObservationV1
stdout  one JSON FilterResultV1 + newline on successful protocol exchange
stderr  protocol/bootstrap diagnostics only
exit 0  protocol exchange completed, including passthrough/failed_open
exit 2  CLI/protocol/bootstrap failure; no FilterResultV1 is emitted
~~~

## ObservationV1

Example:

~~~json
{
  "schema_version": 1,
  "source": "shell",
  "command": "cargo test",
  "shell_dialect": "unknown",
  "output": "test result: ok. 4 passed\n",
  "termination": {
    "kind": "exited",
    "code": 0
  },
  "completeness": "complete",
  "presentation": "unknown"
}
~~~

All top-level fields are explicit. Unknown fields are rejected.

### source

Allowed:

~~~text
shell
read
search
lsp
mcp
browser
other
~~~

### shell_dialect

Allowed:

~~~text
unknown
posix
power_shell
cmd
~~~

### termination

The wire representation is deliberately a strict object rather than an ambiguous nullable exit code.

~~~json
{"kind":"unknown","code":null}
{"kind":"exited","code":0}
{"kind":"aborted","code":null}
{"kind":"timed_out","code":null}
~~~

Rules:

- `exited` MUST carry an integer `code`;
- all other kinds MUST carry `code: null`;
- `unknown` is not success;
- contradictory combinations are protocol-invalid.

### completeness

Allowed:

~~~text
unknown
complete
truncated
~~~

### presentation

Allowed:

~~~text
unknown
terminal_rendered
~~~

A shell source alone does not imply `terminal_rendered`.

## FilterResultV1

WP1.1 currently produces passthrough only. Later engine work may produce normalized/reduced results.

Example passthrough response:

~~~json
{
  "schema_version": 1,
  "decision": "passthrough",
  "replacement": null,
  "profile": null,
  "metrics": {
    "input_bytes": 26,
    "output_bytes": 26,
    "saved_bytes": 0
  },
  "raw_ref": null,
  "diagnostics": []
}
~~~

### decision / replacement contract

| decision | replacement |
|---|---|
| `passthrough` | MUST be null |
| `failed_open` | MUST be null |
| `normalized` | MUST contain replacement text |
| `reduced` | MUST contain replacement text |

Passthrough and failed-open do not echo the original payload across IPC. The adapter already owns it.

### metrics contract

For passthrough/failed-open:

~~~text
output_bytes == input_bytes
saved_bytes == 0
~~~

For normalized/reduced:

~~~text
output_bytes == UTF-8 byte length of replacement
output_bytes <= input_bytes
saved_bytes == input_bytes - output_bytes
~~~

### diagnostics

At most 16 diagnostic codes may be returned.

Protocol V1 recognizes:

~~~text
ambiguous_profile
profile_parse_failed
preservation_failed
input_too_large
raw_store_failed
protocol_warning
incomplete_input
unknown_termination
termination_not_exited
~~~

## Envelope bound

The binary reads at most:

~~~text
128 MiB + 1 byte
~~~

before deciding whether the Protocol V1 envelope exceeds the 128 MiB hard limit. JSON decoding never receives an unbounded stdin stream.

## Strictness

Protocol V1 rejects:

- unsupported `schema_version`;
- malformed JSON;
- multiple JSON values in one envelope;
- unknown Observation/FilterResult/Metrics fields;
- invalid enum values;
- contradictory termination state;
- invalid decision/replacement combinations;
- inconsistent byte metrics;
- more than 16 diagnostics.

Protocol/bootstrap errors are not represented as fabricated `FilterResultV1` values. The host adapter must fail open using the output it already owns.
